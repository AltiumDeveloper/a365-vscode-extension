## Fixed Issues

### WR-01: Active-workspace cue tracks token-exchange events, not user selection

**Files modified:** `src/auth.ts`, `src/sidePanel.ts`
**Commit:** `c10e1c8`
**Applied fix:** Chose reviewer's Option 1 — deleted `GLOBAL_ACTIVE_WORKSPACE_KEY`, removed the writes in `ensureWorkspaceToken` and `clearAllTokens`, and removed the `getActiveWorkspaceId` export (left a deprecation note pointing callers at `getSelectedWorkspace`). The side panel's workspace `getTreeItem` now reads `getSelectedWorkspace(this.ctx)?.workspaceId` to drive the "(active)" cue, which matches what `pickAndExchangeWorkspace` persists and what the script-run pipeline uses via `getSelectedWorkspace`. Eliminates the divergence where expanding a workspace tree node silently flipped the cue.

### WR-02: Tree is not refreshed when active-workspace cue changes

**Files modified:** `src/extension.ts`
**Commit:** `2570641`
**Applied fix:** After `pickAndExchangeWorkspace` returns a token in `doSelectWorkspace`, dispatch `altium365.tree.refresh` so the side panel re-renders and the "(active)" description/icon color follow the user's explicit selection immediately. No new EventEmitter was needed because WR-01's fix made selection the single source of truth and `pickAndExchangeWorkspace` already persists `altium365.selectedWorkspace`; firing the existing refresh command covers all observers cleanly.

### WR-03: Category-node `count` becomes stale after partial refresh

**Files modified:** `src/sidePanel.ts`
**Commit:** `759b863`
**Applied fix:** Refreshing a `projectsCategory` / `scriptsCategory` now clears the corresponding cache *and* fires the change event for the parent workspace node (resolved from `workspacesCache` by `workspaceId`). This causes `loadWorkspaceChildren` to rerun and emit fresh category nodes with recomputed counts, so the row label and the children list stay in sync. If the parent workspace can't be located (e.g. workspaces cache was cleared in between), we fall back to `undefined` which refreshes from root — safe degenerate case.

### WR-04: `openInBrowser` handlers pass backend-supplied URL to `openExternal` without scheme validation

**Files modified:** `src/treeCommands.ts`
**Commit:** `3022e11`
**Applied fix:** Added a shared `openExternalHttpUrl(url, output, logTag)` helper that parses with `vscode.Uri.parse(url, true)` (strict mode — throws on malformed input) and rejects any scheme other than `http`/`https` with a user-visible `showErrorMessage` plus an OutputChannel log line. Both `workspace.openInBrowser` and `project.openInBrowser` now route through this helper instead of calling `vscode.env.openExternal(vscode.Uri.parse(url))` directly. Removes the dependency on VS Code's own non-http(s) confirmation prompt as the sole defense.

## Skipped Issues

### WR-05: `pickAndExchangeWorkspace` reads base token without expiry/refresh check

**File:** `src/workspace.ts:68-75`
**Reason:** Skipped per orchestrator instructions — carry-forward finding from `02-REVIEW.md` (WR-02 in that report). Reviewer explicitly noted "Phase 02.1 did not introduce this defect" and the recommended fix (`getActiveAccessToken(context, cfg)`) has a semantic issue here: `getActiveAccessToken` returns a workspace-scoped token if one is cached, but `listWorkspaces` requires the base (account-scoped) token. A correct fix needs either a new `getRefreshedBaseToken` helper in `auth.ts` (which exports `isExpired`/`refreshTokens` access cleanly) or threading a refresh helper — both expand scope beyond this phase's review boundary. Should be tracked alongside CR-01 / CR-02 / WR-01 / WR-02 carry-forwards from `02-REVIEW.md` in a dedicated auth-hardening pass.
**Original issue:** `pickAndExchangeWorkspace` uses `base.access_token` directly with no `isExpired` check and no refresh attempt. Once the base token expires, "Select Workspace" silently 401s and the user must sign out + in to recover.
