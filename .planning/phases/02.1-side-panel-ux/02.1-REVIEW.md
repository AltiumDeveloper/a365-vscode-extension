# Phase 02.1: Code Review Report

**Reviewed:** 2026-05-20
**Depth:** standard
**Files Reviewed:** 5 (4 sources + package.json)
**Status:** issues_found

## Summary

Phase 02.1 added category-grouped workspace children, a `tree.copyId` command, an active-workspace cue, Open-in-Browser commands, and a globe view/title action. Wiring is clean: new commands are factored into `src/treeCommands.ts` per the convention, menus are correctly gated by `viewItem ==`, GUIDs are removed from labels in favor of a Copy-ID action, and `getActiveWorkspaceId` is a pure read of `globalState`.

The defects concentrate on **state semantics**, not security or storage hygiene. The new active-workspace tracking key (`GLOBAL_ACTIVE_WORKSPACE_KEY`) is updated by `ensureWorkspaceToken` (called on tree-expansion) but **not** by `pickAndExchangeWorkspace` (called by the explicit "Select Workspace" command), so the "(active)" cue diverges from the user's explicit selection. The category-count UX is also susceptible to staleness when only one category is refreshed. No new critical defects, but several real warnings.

Carry-forward findings from `02-REVIEW.md` (CR-01 token-routing collision, CR-02 stale per-workspace tokens across sign-in, WR-01 XSS in OAuth error page, WR-02 raw token in `loadWorkspaces`) are still present in this scope; they are **not** re-listed here per scope but remain unfixed and should be tracked separately.

## Warnings

### WR-01: Active-workspace cue tracks token-exchange events, not user selection (Plan 04 semantic bug)

**File:** `src/auth.ts:296`, `src/auth.ts:373-377`, `src/sidePanel.ts:106-117`, `src/workspace.ts:96-98`
**Issue:**
`GLOBAL_ACTIVE_WORKSPACE_KEY` is written exclusively inside `ensureWorkspaceToken` (line 296). The two real call sites have opposite semantics:

1. `sidePanel.ts:242` — `loadWorkspaceChildren` calls `ensureWorkspaceToken` whenever the user **expands a workspace node in the tree**. The first such expansion writes that workspaceId as "active". On cache hit (subsequent expansions), the line at 296 *still* runs (it's outside the `if (raw)` branch), so every expansion flips the cue.
2. `workspace.ts:96` — `pickAndExchangeWorkspace` (the "Altium 365: Select Workspace" command) calls `exchangeWorkspaceToken` **directly**, bypassing `ensureWorkspaceToken` entirely. So an explicit user selection of workspace B does **not** update the active cue.

Net effect: a user who picks workspace B via the command palette sees workspace A still marked "(active)" because they previously expanded A's tree node. Expanding C in the tree then flips "(active)" to C without any user intent to change selection. The cue does not mean "selected"; it means "most recently expanded or exchanged" — which is not what `getSelectedWorkspace` returns either, so the tree and the script-run pipeline disagree.

**Fix:** Decide what "(active)" means and unify:
- If it means "workspace whose token will be used by script runs", read `getSelectedWorkspace(ctx).workspaceId` in `getTreeItem`, and have `pickAndExchangeWorkspace` write `altium365.selectedWorkspace` (already done) — delete `GLOBAL_ACTIVE_WORKSPACE_KEY` and `getActiveWorkspaceId`.
- If you want both "selected" and "last-exchanged" concepts, gate the write in `ensureWorkspaceToken` to only run when the workspace matches the user's selection, and also write it from `pickAndExchangeWorkspace`.

```ts
// Sketch — option 1, deleting the new key:
// In getTreeItem (sidePanel.ts):
const selected = getSelectedWorkspace(this.ctx);
const isActive = selected?.workspaceId === n.info.workspaceId;
```

### WR-02: Tree is not refreshed when active-workspace cue changes — stale icon until manual refresh

**File:** `src/sidePanel.ts:106-117`, `src/auth.ts:296`
**Issue:**
`getTreeItem` reads `getActiveWorkspaceId(this.ctx)` on every render, but `ensureWorkspaceToken` writes the key without firing any event the tree provider can observe. After expansion of workspace B updates the active id, the workspace-row items (already rendered) are not invalidated. The "(active)" description and icon color of A vs B stay stale until `_onDidChange.fire()` runs (next refresh button, sign-in/sign-out, etc.).

This is independent of WR-01: even if the active-id semantics were correct, the UI would still go stale.

**Fix:** Either (a) fold this concept into `getSelectedWorkspace` and fire `treeProvider.refresh()` from `pickAndExchangeWorkspace`'s caller (which already happens via `onAuthStateChanged` in some flows), or (b) expose an `onDidChangeActiveWorkspace` EventEmitter from `auth.ts` and have `extension.ts` wire it to `treeProvider.refresh()`.

### WR-03: Category-node `count` becomes stale after partial refresh

**File:** `src/sidePanel.ts:80-89`, `src/sidePanel.ts:270-286`
**Issue:**
The category nodes are constructed in `loadWorkspaceChildren` with a literal `count: projectNodes.length` baked into the node object. `refresh(node)` for a `projectsCategory`/`scriptsCategory` clears `this.projectsCache.get(workspaceId)` but does **not** invalidate the parent workspace's children — so the existing category-node instance (with its stale `count`) is reused. On the next expansion of that category, `getChildren` returns `[]` (cache cleared at line 81/86), but the parent still displays `Projects (3)`.

Result: user clicks Refresh on "Projects (3)", sees an empty list under "Projects (3)" — count and contents disagree until a workspace-level or root refresh runs.

**Fix:** Refreshing a category should re-load it and rebuild the category node:
```ts
if (node.kind === 'projectsCategory') {
    this.projectsCache.delete(node.workspaceId);
    // Bubble to the workspace so loadWorkspaceChildren reruns and rebuilds count.
    this._onDidChange.fire(undefined); // or fire the parent workspace node
    return;
}
```
Or move `count` out of the node payload and compute it lazily from `this.projectsCache.get(...)?.length ?? 0` inside `getTreeItem`.

### WR-04: `openInBrowser` handlers pass backend-supplied URL to `openExternal` without scheme validation

**File:** `src/treeCommands.ts:75-83`, `src/treeCommands.ts:106-114`
**Issue:**
`node.url` originates from the GraphQL backend response (`desWorkspaceInfos { url }`, `desProjects { nodes { url } }`). It is parsed by `vscode.Uri.parse(url)` and handed straight to `vscode.env.openExternal`. `Uri.parse` is permissive and will produce URIs for any scheme — `javascript:`, `file:`, `vscode:`, `data:`, etc. If the backend (or a man-in-the-middle on a non-TLS proxy, or a future test environment) ever returns a hostile URL, the extension will obediently launch it. `openExternal` does prompt for non-http(s) schemes in recent VS Code versions, but that is a defense the extension should not depend on.

**Fix:** Whitelist scheme before opening:
```ts
const parsed = vscode.Uri.parse(url, true);
if (parsed.scheme !== 'https' && parsed.scheme !== 'http') {
    vscode.window.showErrorMessage('Altium 365: refusing to open non-http(s) URL');
    return;
}
await vscode.env.openExternal(parsed);
```
Also pass `strict: true` to `Uri.parse` so malformed input throws instead of being silently coerced.

### WR-05: `pickAndExchangeWorkspace` reads base token without expiry/refresh check (carry-forward, still in scope)

**File:** `src/workspace.ts:68-75`
**Issue:**
`pickAndExchangeWorkspace` calls `getStoredTokens(context)` and uses `base.access_token` directly against `listWorkspaces`. There is no `isExpired` check and no refresh-token attempt, mirroring the `loadWorkspaces` issue called out as WR-02 in `02-REVIEW.md`. Once the base token expires, "Select Workspace" silently 401s and the user must sign out + in to recover. Phase 02.1 did not introduce this defect, but it touches the same surface area as the new active-workspace work; worth flagging again so it isn't lost.

**Fix:** Replace with `getActiveAccessToken(context, cfg)` (or thread a refresh helper). Same pattern as the suggested fix for `loadWorkspaces`.

## Info

### IN-01: `workspaceUrl` fallback derivation is a no-op against real endpoints

**File:** `src/sidePanel.ts:227`
**Issue:**
```ts
const workspaceUrl = endpoint.replace(/\/api(\/.*)?$/, '') || endpoint;
```
The configured endpoints (e.g. `https://usw2.dev-365.altium.com/napi/gateway/graphql`) contain no `/api` segment, so this regex never matches and `workspaceUrl` is always the verbatim GraphQL endpoint URL. If `info.url` is missing and any downstream code ever opens `workspaceUrl` in a browser, the user will land on a GraphQL endpoint that responds with JSON/4xx. The fallback gives a false sense of safety.

**Fix:** Either compute a real human URL from `endpoint` (e.g. derive `https://<host>` for the workspace landing page), or drop the fallback and let the caller treat "missing url" as "no Open in Browser action available" (which Plan 05's URL-missing branch already does at the command level).

### IN-02: `workspaceUrl` field on `script` nodes is unused

**File:** `src/sidePanel.ts:38-47`, `src/sidePanel.ts:263-269`

The `script` node carries `workspaceUrl`, but no command in `treeCommands.ts` (or anywhere in this phase's scope) reads it. It's reserved for future "Open Script in Browser" work but currently inflates the node payload and the discriminated-union type with unused state. If it's intentional pre-wiring, leave a TODO citing the future plan.

### IN-03: `altium365.tree.copyId` silently no-ops when id is missing

**File:** `src/treeCommands.ts:43-48`
**Issue:**
When the resolved id is `undefined` (e.g. a script row whose `scriptId` was null in the GraphQL response, or a defensive guard against a future node kind that lacks an id), the handler only writes to the OutputChannel. The user clicks "Copy ID", sees no feedback, and assumes clipboard now holds the previous value. At minimum show a warning toast.

**Fix:**
```ts
if (!id) {
    vscode.window.showWarningMessage('Altium 365: no ID available for this item');
    output.appendLine(...);
    return;
}
```

### IN-05: Active vs inactive workspace icon uses the same codicon — visual cue is subtle

**File:** `src/sidePanel.ts:108-116`
**Issue:**
The comment claims "filled cloud + (active)" vs "dimmed cloud", but both branches use `new vscode.ThemeIcon('cloud', ...)`. There is no filled/outline variant — only the `ThemeColor` differs (default vs `descriptionForeground`). On many themes the contrast between these two colors is minimal, and the cue largely reduces to the `(active)` suffix text. Either acknowledge that in the comment or pick a stronger visual (e.g., add `item.resourceUri`/`item.iconPath = new vscode.ThemeIcon('cloud', new vscode.ThemeColor('charts.blue'))` for active).

**Fix:** Update the comment to reflect reality, or upgrade the active state's `ThemeColor` to something like `'charts.blue'` or `'list.highlightForeground'` for a clearer signal.

### IN-06: Redundant `"icon"` on `view/title` menu entry

**File:** `package.json:272-277`
**Issue:**
The hotfix correctly added `"icon": "$(globe)"` to the command definition at `package.json:75`, which is what `view/title` rendering reads. The same `"icon"` is also set on the menu contribution at line 276. VS Code's menu schema doesn't define `icon` on `view/title` items (it's read from the command), so the menu-level field is silently ignored. Harmless, but noise — and confusing if the two ever drift.

**Fix:** Remove the menu-level `"icon"` field (keep only the command-level one).
