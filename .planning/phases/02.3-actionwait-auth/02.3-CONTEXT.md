# Phase 02.3 — ActionWait Auth Flow — CONTEXT

## Source flow (user-provided, 2026-05-20)

1. Desktop generates `connection_token` (GUID) and PKCE pair (`code_verifier`, `code_challenge = sha256(code_verifier)`)
2. Desktop opens a long-poll connection to `actionWaitEndpoint` keyed by `connection_token`
3. Desktop opens browser to `<authEndpoint>?...` with: `code_challenge`, `code_challenge_method=S256`, `client_id`, `state=<connection_token>`, **fixed** `redirect_uri=<authCompletedUrl>`, `response_type=code`, `scope`
4. User authenticates in browser (any of the 4 UnifiedLogin methods)
5. UnifiedLogin redirects to `<authCompletedUrl>` with `code` + `state` (= connection_token) in query string
6. UnifiedLogin server POSTs `{code, connection_token}` to ActionWait `/Provide` (server-to-server, NOT browser-to-ActionWait)
7. ActionWait releases the long-poll, returning `code` to desktop
8. Desktop exchanges `code` at `tokenEndpoint` with `code_verifier` + same `redirect_uri` → JWT

## Decisions (LOCKED)

- **D-01:** OAuth `redirect_uri` is env-specific (mirrors `authEndpoint` host): `https://auth.dev1.altium.com/authCompleted`, `https://auth.uat1.altium.com/authCompleted`, `https://auth.altium.com/authCompleted`. Each must be registered as an allowed redirect URI in its respective auth client.
- **D-02:** Add `redirectUri: string` to `EnvironmentSpec` and to `package.json` `altium365.environments[*]` schema. Defaults populated for the three known envs in `package.json` `default`.
- **D-03:** Remove `altium365.redirectPort` and `altium365.redirectPath` settings from `package.json contributes.configuration` entirely (no deprecation period — pre-release extension).
- **D-04:** Remove `redirectPort` and `redirectPath` from the `OAuthConfig` type and from `readOAuthConfig`. Add `actionWaitEndpoint: string` and `redirectUri: string`.
- **D-05:** ActionWait long-poll **transport details are a research item.** Working assumptions until verified: HTTP `GET <actionWaitEndpoint>?token=<connection_token>` returning JSON `{code: string, state: string}` on completion; server holds the connection open up to its own timeout (assumed 60–120 s); on server-side timeout (e.g. HTTP 204 / empty 200 / specific status), the client reconnects with the SAME `connection_token` and continues polling until the overall sign-in timeout (180 s default) or user cancellation. Executor MUST verify the actual contract against an Altium-provided sample request or the ActionWait OpenAPI before writing the poll loop. If the verb / shape / status differ, update the implementation and document the deviation in SUMMARY without re-running discuss.
- **D-06:** `connection_token` generation: `crypto.randomUUID()` (Node 18+, already required by extension; no new dep). 36-char UUID v4.
- **D-07:** `connection_token` doubles as the OAuth `state` parameter. CSRF check: the value returned by ActionWait MUST match the value sent. Mismatch → reject sign-in with `Error('State mismatch (possible CSRF).')` — same wording as the loopback flow used.
- **D-08:** `clientId` stays a single global setting (user confirmed identical across dev/uat/prod). CONCERNS.md gap is OUT OF SCOPE for this phase.
- **D-09:** Sign-in is wrapped in `vscode.window.withProgress({location: vscode.ProgressLocation.Notification, cancellable: true, title: 'Altium 365: waiting for sign-in...'})`. User cancellation:
  - Pass an `AbortSignal` (from `AbortController`, wired to `progress.token.onCancellationRequested`) into the poll loop.
  - On cancel: abort the in-flight fetch, do NOT exchange any code, reject `signIn` with `Error('Sign-in cancelled.')`.
  - Do NOT mutate stored tokens on cancel (`clearAllTokens` at entry has already drained prior state per D-05 of Phase 02.2 — that pre-drain is intentional and preserved).
- **D-10:** Remove `awaitCallback` and `escapeHtml` entirely. No HTML response page (the browser sees Altium's `authCompleted` page, which Altium owns per user's prior decision in this session).
- **D-11:** New private module-local function in `src/auth.ts` (NOT a new file) — keep auth surface contained in one file consistent with project convention:
  ```
  async function pollActionWait(
    endpoint: string,
    connectionToken: string,
    signal: AbortSignal,
    timeoutMs: number
  ): Promise<{ code: string; state: string }>
  ```
  Internally loops `fetch` calls until completion / cancel / overall-timeout. Uses `signal` to abort, honours `timeoutMs` as a wall-clock cap.
- **D-12:** Error mapping (each gets a distinct user-facing message via `vscode.window.showErrorMessage` at the `signIn` call site in `src/extension.ts`):
  - Cancellation → silent (no error toast; the progress notification closing is the feedback)
  - Network error during poll → `Altium 365 sign-in failed: cannot reach ActionWait service (<host>). Check network connectivity.`
  - ActionWait 4xx/5xx → `Altium 365 sign-in failed: ActionWait returned <status>.` (response body truncated to 500 chars per Phase 02.2 D-12 pattern)
  - Overall timeout → `Altium 365 sign-in timed out after 3 minutes. Please try again.`
  - State mismatch → `Altium 365 sign-in failed: state mismatch (possible CSRF).` Token exchange NOT attempted.
  - Token-endpoint failure → existing `postForm` error surfaces unchanged (already handled by Phase 02.2 hygiene).
- **D-13:** Phase 02.2 auth-hardening surface is **invariant**:
  - `getBaseAccessToken` / `getActiveAccessToken` / `ensureWorkspaceToken` / `workspaceTokenMutex` / `AsyncMutex` — UNCHANGED
  - `clearAllTokens(context, {silent: true})` pre-drain at top of `signIn` — UNCHANGED (still runs before the ActionWait dance)
  - Token storage format (`SECRET_TOKENS` JSON-encoded TokenSet) — UNCHANGED
  - `getStoredTokens`, `getStoredWorkspaceToken`, the per-workspace index, the auth state emitter, `decodeIdTokenClaims`, `userLabelFromClaims` — UNCHANGED
- **D-14:** Manual UAT only — no automated tests for the poll loop. Scenarios (≥5):
  1. Happy path: sign-in completes against ActionWait in each of dev/uat/prod (3 sub-runs)
  2. User cancels via progress notification → silent abort, no token stored
  3. User closes browser tab before authorising → eventual overall-timeout error after 180 s
  4. State mismatch: manually craft a callback where ActionWait returns a different state → CSRF error, no token exchange
  5. Network failure during poll (disable network mid-flow) → user-facing network error
  6. Phase 02.2 regression sanity: token routing / workspace expansion / sign-out still work after a successful ActionWait sign-in
- **D-15:** `actionWaitEndpoint` URLs in `package.json` (committed `e445252`) are taken as-is. If they prove wrong during UAT, fix forward in this phase.
- **D-16:** Use `globalThis.fetch` (Node 18+ native) for ActionWait poll. No new HTTP client dependency. Consistent with `postForm` in `src/auth.ts:117-127` which already uses `fetch`.

## Research items for planner / executor

The following MUST be confirmed against Altium docs or a working reference implementation **before** the poll loop is written. Planner should allocate a research/spike task or include verification steps in the first plan.

1. **HTTP verb** for the long-poll call (GET vs POST)
2. **Request shape**: connection_token in query string, header, or POST body? Header name?
3. **Response shape on completion**: JSON body? Fields exactly named `code` and `state`, or something else?
4. **Server-side timeout signal**: what status / body indicates "no callback yet, reconnect"? Is it 204, 200-with-empty-body, 408, custom JSON `{status: 'pending'}`?
5. **Reconnect semantics**: does the same `connection_token` survive multiple GETs, or must each reconnect mint a new token?
6. **Error response shapes** for invalid/expired connection_token, malformed request, server error
7. **CORS / auth headers required on the poll call** (likely none — the connection_token IS the auth — but verify)

If Altium docs are not accessible, derive shapes from a working sample (the executor can capture the actual request a known-good client makes against dev1 and use that as the contract).
