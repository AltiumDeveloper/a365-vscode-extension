# Phase 02.3 — ActionWait Auth Flow: Manual UAT

> **Closure note (2026-05-20):** Operator ran a representative subset of
> scenarios live against `dev1` and explicitly accepted closing the phase
> without exhaustively re-running all 8 scenarios. Findings from the partial
> run were fixed in-phase (commits `6faceb6`, `d047553`, `a89d4e3`,

Manual UAT per D-14 — **no automated tests for the poll loop**. Operator must record
pass/fail for each scenario below before the phase is closed. The negative scenarios
quote D-12's verbatim user-facing error strings so cross-checking is unambiguous; the
regression scenario explicitly probes Phase 02.2 auth-surface invariants (D-13).

Run scenarios in order. For each, tick **PASS** or **FAIL**. Capture failure details in
the "Sign-off" section at the bottom.

Setup once before starting:

1. Build a fresh VSIX or launch the Extension Development Host (F5) against a fresh
   build (`npm run compile`).
2. Open the OutputChannel: View → Output → select **Altium 365** from the dropdown.
3. Open the Developer Tools: Help → Toggle Developer Tools → **Network** tab, filter
   for the active environment's GraphQL endpoint, token endpoint, and `actionWaitEndpoint`.
4. Confirm `altium365.environments` is populated (Phase 01 defaults: `dev1`, `uat1`,
   `prod`) and `altium365.clientId` is set.
5. Confirm the D-01 redirect URIs are registered as allowed redirect URIs in their
   respective Altium auth clients:
   - dev1 → `https://auth.dev1.altium.com/authCompleted`
   - uat1 → `https://auth.uat1.altium.com/authCompleted`
   - prod → `https://auth.altium.com/authCompleted`

## Scenario 1.a — Happy path against `dev1` (D-14.1)

**Preconditions**

- Extension installed and enabled; OutputChannel open.
- `altium365.environments` includes the `dev1` entry with its `authEndpoint`,
  `tokenEndpoint`, `actionWaitEndpoint`, and `redirectUri =
  https://auth.dev1.altium.com/authCompleted` (D-01).
- `altium365.clientId` is set to the global client (D-08).
- The dev1 auth client has `https://auth.dev1.altium.com/authCompleted` registered as
  an allowed redirect URI.

**Steps**

1. Run `Altium 365: Select Environment` and pick `dev1`.
2. Confirm the post-switch "Sign out & sign in" prompt OR run `Altium 365: Sign In`
   manually.
3. Observe that the system browser opens to the dev1 `authEndpoint` URL and the
   `redirect_uri` query parameter is `https://auth.dev1.altium.com/authCompleted` (D-01).
4. Complete UnifiedLogin in the browser (any of the four supported methods).
5. Browser lands on `https://auth.dev1.altium.com/authCompleted`.
6. Switch back to VS Code.

**Expected**

- A progress notification titled **"Altium 365: waiting for sign-in..."** appears with
  a **Cancel** button as soon as `Sign In` is invoked (D-09), and closes silently on
  success.
- A toast **"Altium 365: signed in."** fires.
- The `altium365.signedIn` context becomes `true` (status-bar / Activity Bar view
  updates accordingly).
- **No local HTTP server** is started by the extension during sign-in — verify with
  `lsof -iTCP -sTCP:LISTEN -P 2>/dev/null | grep -i code` (or platform equivalent)
  showing no extension-spawned listener around the previously-used OAuth port range
  (loopback flow removed per D-10).

**Pass criteria**

- All six steps succeed end-to-end.
- No errors in the **Altium 365** output channel.
- A workspace can be selected and expanded post-sign-in (proves the token is valid
  and that the Phase 02.2 token-exchange path still works).

**Preconditions**

- Not signed in to the active environment. Run `Altium 365: Sign Out` first if
  needed.

**Steps**

1. Run `Altium 365: Sign In`.
2. Wait for the progress notification **"Altium 365: waiting for sign-in..."** to
   appear. Do **not** touch the browser tab that opens.

**Expected**

- **No error toast appears** — cancellation is silent per D-12 (the closing of the

  start the full browser dance, not short-circuit on a cached token.

- Silent cancellation (no `Altium 365 sign-in failed:` toast at all).
- `getStoredTokens` returns undefined — verified indirectly by the subsequent sign-in
  re-running the full browser flow and progress notification, rather than producing
  an immediate "signed in" toast.

  to drain on the next reconnect cycle).

## Scenario 4 — State mismatch (CSRF guard) (D-14.4)

**Preconditions**

- Developer access to the extension source or the running debug session — this
  scenario cannot be triggered against production ActionWait under normal flow, so a
  manual intercept / debugger workaround is required.
- Not signed in to the active environment.

**Steps**

Pick **one** of the two acceptable methods below and document which was used in the
Sign-off notes:

- **(a) Debugger method.**
  1. Launch the Extension Development Host (F5) in VS Code with `src/auth.ts` open.
  2. Set a breakpoint in `pollActionWait` (D-11) **immediately after the 200 response
     body is parsed** — i.e. on the line that returns `{ code, state }` from the
     successful branch.
  3. Run `Altium 365: Sign In` and complete UnifiedLogin in the browser as normal.
  4. When the breakpoint hits, in the debug console mutate the parsed `state` field
     to a different UUID (e.g. `crypto.randomUUID()`).
  5. Resume execution.

- **(b) Local intercept method.**
  1. Run `mitmproxy` (or equivalent) on the active env's `actionWaitEndpoint`.
  2. Configure the proxy to rewrite the JSON response body of the long-poll's 200
     completion to substitute a **different** value for the `state` field while
     leaving everything else intact.
  3. Run `Altium 365: Sign In` and complete UnifiedLogin.

**Expected**

- `signIn` rejects with `Error('State mismatch (possible CSRF).')` (D-07 wording —
  same string the previous loopback flow used).
- The call site in `src/extension.ts` surfaces this as an error toast with the **exact**
  D-12 wording:

  > Altium 365 sign-in failed: state mismatch (possible CSRF).

- **Token exchange is NEVER attempted.** Verify in the Network tab / output channel:
  there is **no POST to the active env's `tokenEndpoint`** after the mutated 200
  response is received.
- No token is stored.

**Pass criteria**

- Error toast text matches **"Altium 365 sign-in failed: state mismatch (possible
  CSRF)."** verbatim per D-12 (and the internal exception message matches D-07).
- **Zero requests** to the `tokenEndpoint` appear in the network log.
- No token is written to SecretStorage.

- [ ] PASS
- [ ] FAIL

## Scenario 5 — Network failure during poll (D-14.5)

**Preconditions**

- A way to disable network connectivity mid-flow (Wi-Fi toggle in the OS, `nmcli`,
  airplane mode, system network settings, etc.).
- Not signed in to the active environment.

**Steps**

1. Run `Altium 365: Sign In`.
2. Wait for the browser to open and the long-poll to start (visible as an outgoing
   POST to the active env's `actionWaitEndpoint` in the Network tab).
3. Disable the network connection.
4. Wait for the current poll cycle to attempt its next fetch (within ~150 s — the
   per-request timeout / 408-reconnect cycle defined in D-05).

**Expected**

- An error toast appears with the **exact** D-12 wording (with the actionWaitEndpoint
  host interpolated for the active env):

  > Altium 365 sign-in failed: cannot reach ActionWait service (`<host>`). Check
  > network connectivity.

  Example for `dev1`: the `<host>` is the hostname of the env's `actionWaitEndpoint`.
- No token is stored in SecretStorage.
- Progress notification closes.

**Pass criteria**

- Error toast text matches **"Altium 365 sign-in failed: cannot reach ActionWait
  service (`<host>`). Check network connectivity."** with the correct host
  interpolated for the active environment per D-12.
- No token written to SecretStorage.
- After restoring the network and re-running `Altium 365: Sign In`, sign-in succeeds
  end-to-end.

## Scenario 6 — Phase 02.2 regression sanity (D-14.6)

**Preconditions**

- A successful sign-in just completed (Scenario 1.a passed).
- Activity Bar Altium 365 view is available.

**Steps**

1. Open the Altium 365 Activity Bar view.
2. Expand the workspaces tree (this triggers `listWorkspaces` via the **base** token —
   Phase 02.2 D-03/D-09/D-10).
3. Expand a workspace (this triggers `ensureWorkspaceToken` and the per-workspace
   token exchange — Phase 02.2 D-07).
4. Confirm projects / scripts load under the expanded workspace.
5. Run `Altium 365: Sign Out`.
6. Confirm the tree empties and `altium365.signedIn` context flips to `false`.
7. Run `Altium 365: Sign In` again and confirm the full ActionWait flow works a
   second time.

**Expected**

- Workspaces list loads without error (no 401).
- The per-workspace token is fetched on demand — visible as a **separate
  `/connect/token` POST** in the Network tab (or in the OutputChannel if verbose
  logging is enabled).
- Sign-out clears **both** the base token (`altium365.tokens`) **and every
  per-workspace token** (`altium365.workspaceTokens.*` and its `__index` entry) from
  SecretStorage — preserving the Phase 02.2 CR-01 / WR-05 invariant.
- After re-sign-in (step 7), re-expanding the same workspace triggers a **fresh**
  token-exchange POST against `tokenEndpoint`, **not** a cache hit from the previous
  identity (proves that sign-out did drain per-workspace tokens, not just the base).
- The auth-state emitter fires the expected `signedIn: false` event on sign-out and
  `signedIn: true` event on re-sign-in.

**Pass criteria**

- No 401 errors at any point in the flow.
- **No carry-over** of per-workspace tokens across sign-out — Phase 02.2 CR-01 / WR-05
  stays closed.
- Re-sign-in succeeds end-to-end (full ActionWait progress notification + sign-in
  toast), and the post-re-sign-in workspace expansion produces a fresh token
  exchange.
