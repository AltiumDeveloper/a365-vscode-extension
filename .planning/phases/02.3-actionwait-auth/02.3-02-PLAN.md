       ```
       if (spec.actionWaitEndpoint !== undefined) {
           await cfg.update('actionWaitEndpoint', spec.actionWaitEndpoint, target);
       }
       if (spec.redirectUri !== undefined) {
           await cfg.update('redirectUri', spec.redirectUri, target);
       }
       ```
       Use the same conditional `!== undefined` pattern the existing scopes/audience block uses — DO NOT mirror the unconditional `?? ''` pattern used for the three core endpoints. Reason: an empty-string default would mask a misconfigured env, while leaving the previous setting in place lets the user see the validation failure later (in plan 04's readOAuthConfig) with a meaningful value to debug.

    Also extend the diagnostic logging block (lines 246-249) to surface the two new endpoints alongside the existing graphql/auth/token lines. Add two appendLine calls after the `token:` line:

    ```
    outputChannel.appendLine(`[Altium 365]   redirect:   ${spec.redirectUri || '(empty)'}`);
    ```
    This mirrors the existing log style (column-aligned key, `(empty)` fallback) and gives UAT scenario D-14.1 a one-glance way to confirm the right env was selected.

    Do NOT extend the validation warning at lines 209-225. The current warning only fires when graphql/auth/token are missing because those three are unrecoverable; missing actionWaitEndpoint or redirectUri will be caught by plan 04's `readOAuthConfig` and surfaced via plan 05's pre-flight check in `doSignIn`. Splitting the validation responsibility keeps the env-switch warning narrow and the sign-in pre-flight authoritative.
