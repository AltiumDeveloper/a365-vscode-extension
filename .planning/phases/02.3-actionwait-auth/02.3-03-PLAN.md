    - Preconditions: extension installed, `altium365.environments` populated (plan 01 defaults), `altium365.clientId` set, target env's auth client has the D-01 redirectUri registered as an allowed redirect URI.
    - Steps: (1) Run `Altium 365: Select Environment`, pick the target env. (2) Confirm the post-switch "Sign out & sign in" prompt OR run `Altium 365: Sign In` manually. (3) Browser opens to the env's `authEndpoint` with the D-01 redirectUri in the URL bar. (4) Complete UnifiedLogin. (5) Browser lands on `<env>/authCompleted`. (6) VS Code shows "Altium 365: signed in." toast.
    - Expected: progress notification "Altium 365: waiting for sign-in..." appears with a Cancel button, then closes silently on success; sign-in toast fires; `altium365.signedIn` context becomes true (status-bar / view updates); no local HTTP server is started (verify with `lsof -iTCP -sTCP:LISTEN -P 2>/dev/null | grep -i code` showing no extension-spawned listener around the OAuth port range).
    - Pass criteria: all six steps succeed, no errors in the Altium 365 output channel, a workspace can be selected and expanded post-sign-in (proves the token is valid).

    **Scenario 2 — User cancels via progress notification** (D-14.2):
    - Preconditions: not signed in (run sign-out first if needed).
    - Steps: (1) Run `Altium 365: Sign In`. (2) Wait for the progress notification to appear; do NOT touch the browser. (3) Click the Cancel button on the notification.
    - Expected: progress notification closes immediately. NO error toast appears (D-12 → cancellation is silent). NO token is stored (verify by running `Altium 365: Sign In` again — it must start fresh, not short-circuit on a cached token).
    - Pass criteria: silent cancellation; no `Sign-in failed:` toast; `getStoredTokens` returns undefined (proxy check: subsequent sign-in shows the full browser dance, not a cached-token path).

    **Scenario 3 — Browser tab closed before authorising → overall timeout** (D-14.3):
    - Preconditions: not signed in.
    - Steps: (1) Run `Altium 365: Sign In`. (2) Browser tab opens; close it immediately without authenticating. (3) Wait 3 minutes (180 s wall-clock cap per D-09 / signIn default `timeoutMs`).
    - Expected: progress notification stays open for the full 180 s. After timeout, an error toast appears with the exact text per D-12 → "Altium 365 sign-in timed out after 3 minutes. Please try again." No token is stored.
    - Pass criteria: error message text matches D-12 verbatim; timeout fires at ~180 s (±30 s tolerance for the in-flight poll request to drain); no token leaks into SecretStorage.

    **Scenario 4 — State mismatch (CSRF guard)** (D-14.4):
    - Preconditions: developer access to source / debugger to manipulate the response.
    - Steps: this scenario CANNOT be triggered against production ActionWait under normal flow. Instead, document two acceptable methods:
      - (a) **Debugger method**: set a breakpoint in `pollActionWait` immediately after parsing the 200 response, mutate the parsed `state` field to a different UUID before it returns. Resume execution.
      - (b) **Local intercept method**: run a local proxy (e.g. `mitmproxy`) on the actionWaitEndpoint and rewrite the JSON response body to substitute a different state value.
    - Expected: signIn rejects with `Error('State mismatch (possible CSRF).')` (the D-07 wording); call site shows toast "Altium 365 sign-in failed: state mismatch (possible CSRF)." per D-12; token exchange is NEVER attempted (verify by checking the network panel / output channel — no POST to tokenEndpoint).
    - Pass criteria: CSRF error wording matches D-07/D-12; no token endpoint POST occurs; no token is stored.

    **Scenario 5 — Network failure during poll** (D-14.5):
    - Preconditions: a way to disable network mid-flow (Wi-Fi toggle, `nmcli`, system network setting).
    - Steps: (1) Run `Altium 365: Sign In`. (2) Wait for browser to open and the long-poll to start. (3) Disable the network connection. (4) Wait for the current 408-reconnect cycle to attempt its next fetch (≤ ~150 s).
    - Expected: error toast with the D-12 wording: "Altium 365 sign-in failed: cannot reach ActionWait service (<host>). Check network connectivity." where `<host>` is the actionWaitEndpoint host for the active env. No token is stored. Progress notification closes.
    - Pass criteria: error message text matches D-12 with the correct host interpolated; user can re-run sign-in after restoring network.

    **Scenario 6 — Phase 02.2 regression sanity** (D-14.6):
    - Preconditions: a successful sign-in just completed (scenario 1.a passed).
    - Steps: (1) Open the Altium 365 Activity Bar view. (2) Expand the workspaces tree (this triggers `listWorkspaces` via the base token). (3) Expand a workspace (this triggers `ensureWorkspaceToken` token exchange). (4) Confirm projects/scripts load. (5) Run `Altium 365: Sign Out`. (6) Confirm tree empties and `altium365.signedIn` context flips false. (7) Run `Altium 365: Sign In` again and confirm the full flow works a second time.
    - Expected: workspaces list loads without error; per-workspace token is fetched on demand (visible as a separate `/connect/token` POST in the output channel if logging is verbose); sign-out clears both base and per-workspace SecretStorage entries (verify: the workspace re-expansion after re-sign-in triggers a fresh exchange, not a cache hit from the previous identity); the auth-state emitter fires the expected signedIn:false then signedIn:true events.
    - Pass criteria: no 401 errors mid-flow; no carry-over of workspace tokens across sign-out (Phase 02.2 CR-01 / WR-05 stays closed); re-sign-in succeeds end-to-end.
