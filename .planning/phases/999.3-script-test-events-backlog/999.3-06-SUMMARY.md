## Issues Encountered

**UAT iter 1 — LanguageStatusItem invisible.** First-cut placement used `vscode.languages.createLanguageStatusItem` at Information severity, which VS Code collapses behind the `{}` icon. **Fix:** switched to `vscode.window.createStatusBarItem(id, Right, 100)` gated on `languageId === 'python'`.

**UAT iter 3 — Wrong workspace for projects.** `pickProjectIdSafe` assumed the active workspace, which is wrong when the user has a remote script open from workspace B while workspace A is active. **Fix:** extended `ScriptIdentity.remote` with optional `workspaceAuthId`; refactored `pickProjectIdSafe` into three branches that prefer the script's own workspace, then active, then Select-or-Manual.

**UAT iter 4 — Status bar click was a no-op.** Wired to a transient `testEvents.pick` that returned a body without mutating store → indicator never updated. **Fix:** rewired to `testEvents.setDefault`.

**UAT iter 5 — Picker had three half-overlapping actions.** "Edit current default", "Edit any", "Set default" felt redundant. **Fix:** collapsed to one unified picker — picking an event SETS DEFAULT; Create / Edit / Delete are dispatched to dedicated commands.

**UAT iter 6 — Two deprecated settings still in package.json.** `altium365.inputParametersPath` (replaced by test events) + `altium365.promptForProjectId` (no-op since D-22, Phase 6). **Fix:** removed both end-to-end with no back-compat shim (no active users).

**UAT iter 7 — Edit shows empty payload.** Picker preview showed correct event body, but opening Edit showed `{$schema:..., }` only. **Root cause:** `vscode.Uri.parse('altium365-event://<identity>/...')` lowercases the authority per RFC 3986 §3.2.2; if the original identity had uppercase chars (UUID hex), `readStore` lookup missed the original-case store key. **Fix 7a:** moved identity to first path segment (path segments are case-preserved). **Fix 7b:** switched constructor to `vscode.Uri.from({ scheme, path })` — `Uri.parse` with single-slash `:/foo` form throws "path cannot begin with //" when re-parsed after `toString` round-trip via `openTextDocument`.

## A/B Trial Observations (Placement A submenu vs Placement B title-bar button)

Plan asked for an explicit A vs B comparison. UAT outcome:

- **Placement B (sibling title-bar button)** was redundant once the status bar indicator landed. Removed in UAT iter 5 (`e57d316`).
- **Placement A (submenu sub-row under `4_events@1`)** retained — discoverable via the existing Altium 365 editor-title submenu without consuming a top-level icon slot.
- **Status bar indicator** ended up as the primary affordance — visible at all times, shows count + default at a glance, click opens the unified picker.

**Recommendation for a future phase:** Placement B was a net negative once the status bar shipped. Keeping submenu (A) + status bar is the right long-term placement. No further A/B work needed.
