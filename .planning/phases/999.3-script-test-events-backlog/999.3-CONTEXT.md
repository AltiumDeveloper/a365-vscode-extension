# Phase 999.3: Script Test-Events - Context

**Gathered:** 2026-05-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the ad-hoc parameter handling shipped through Phases 3–6 with a named **test-events** model — multiple parameter templates per script, shared identically across local run, local debug, and remote execute. Inspired by AWS Toolkit's Lambda test events.

**What this phase delivers (in scope):**

1. **Unified storage** — replace today's three divergent sources (workspaceState blob for remote, sibling `.params.json` for local, projectId-prompt fallback shipped in Phase 6) with a single per-script test-events blob.
2. **Shared resolver** — `resolveScriptParameters(scriptIdentity)` consumed identically by `prepareRun` (local run/debug) and `executeRemoteScript`'s Block B (remote execute). Eliminates the divergence Phase 6 D-05 only patched at the surface.
3. **Default-event semantics** — silent default for unattended invocations; first-run prompt to create or pick.
4. **Built-in `project-related` preset** — reproduces today's `{projectId: <picked>}` payload using `pickProjectId`. User can edit/clone.
5. **Sibling `.params.json` migration** — one-time import prompt; state wins thereafter.
6. **Editor UI** — JSON virtual document with JSONSchema validation.
7. **Picker surfaces** — both submenu sub-row AND separate title-bar dropdown, shipped together for A/B trial.

**Not in this phase (Deferred Ideas):**

- Cross-user event sharing (round-trip via remote-stored blob)
- Hard storage caps / quota enforcement (soft warning only in v1)
- Structured form WebView editor (JSON suffices for v1)
- Migration of existing flat `*.params.json` files beyond first-run prompt
- Schema authoring tools for script-specific param shapes (only the built-in `project-related` shape ships with JSONSchema)

</domain>

<decisions>
## Implementation Decisions

### Storage

- **D-01:** **`globalState`, not `workspaceState`.** Test events follow the user across all VS Code windows. Same mental model as the existing `lastProjectId` cache (`extension.ts:831` uses `context.globalState.get/update` despite the misleading comment at `remoteExecution.ts:175` calling it `workspaceState` — the comment is wrong, the code is right). Phase 3 D-05's reservation mentioned `workspaceState`; this phase supersedes that.
- **D-02:** **Storage key:** `altium365.scriptParams.<identity>`. The prefix is reserved per Phase 3 D-05 and Phase 6 D-23; this phase activates it.
- **D-03:** **Storage shape (locked from roadmap item 1):** `{ defaultEventName: string, events: { [name: string]: object } }`. One default event marked for unattended runs (palette commands, submenu invocations, no UI prompt).

### Identity (script-key derivation)

- **D-04:** **Unified per-script model — same UX for remote and standalone local scripts.** `identity = scriptId` for scripts with a remote identity (in `localScriptCache` or otherwise a remote-tmp file); `identity = fsPath` for standalone local `.py` files.
- **D-05:** **fsPath fragility is accepted.** Moving a standalone `.py` file orphans its events on the old path. Worst case: user recreates events on the new path. No content-hash, no workspace-relative path tricks — explicit simplicity over edge-case robustness.
- **D-06:** **`resolveScriptIdentity(uri)` helper** — single source of truth that returns `{ kind: 'remote' | 'local', identity: string }`. Branches on `localScriptCache` membership exactly like Phase 6's `activeIsRemoteScript` context-key logic. Reused by all four entry points: `prepareRun`, `executeRemoteScript`, the events picker, and the editor.

### Sibling `.params.json` interop

- **D-07:** **One-time import prompt, then state wins.** On first invocation of a local `.py` where (a) a sibling `<name>.params.json` exists AND (b) no globalState entry exists for that identity, prompt: "Import `<name>.params.json` as a test event?" with name input (default: `imported`). On confirm, file contents become a named event in globalState.
- **D-08:** **File is NOT deleted after import.** Set a per-identity marker (`altium365.scriptParams.importedFrom.<identity>` = absolute file path) so we don't re-prompt. Subsequent runs read globalState only; the sibling file is ignored. Trade-off: file may drift from state, but deleting user files is a hard no.
- **D-09:** **`inputParametersPath` setting still wins when explicitly set.** The existing `altium365.inputParametersPath` workspace setting is an escape hatch for power users; if set, it bypasses the entire test-events flow. Document this in the setting description.

### Default-event invocation semantics

- **D-10:** **Silent default everywhere.** All four entry points (Run Local / Debug Local / Execute Remote from submenu rows; `altium365.runScript` / `altium365.debugScript` / `altium365.script.executeRemote` from Command Palette) use the script's `defaultEventName` silently. No QuickPick on every invocation.
- **D-11:** **First-run prompt only.** When no events exist for an identity, prompt to create one (with `project-related` preset offered as a default option). If events exist but no `defaultEventName` is set, prompt to pick which to use as default. Subsequent runs are silent.

### UI surfaces

- **D-12:** **Ship both placements in v1; pick one in cleanup.** Both wired to the same commands — only `package.json` menu contributions differ. The user wants to compare visually before removing one.
  - **Placement A (submenu sub-row):** A new row `"Test events ▸"` appended to `altium365.editorTitle` after the existing 4 rows (group `4_events@1`). Expands to: event name list (click = set as default) + separator + `Create new…` + `Edit current…` + `Delete…`. Reuses the Phase 6 branded submenu container.
  - **Placement B (separate title-bar dropdown):** A second `editor/title` entry next to the Altium 365 submenu icon — its own button with a lightning-bolt icon (or similar), opening the same picker. Same `when:` clause as the submenu (`resourceLangId == python`).
- **D-13:** **Shared command IDs:** `altium365.testEvents.pick`, `altium365.testEvents.create`, `altium365.testEvents.edit`, `altium365.testEvents.delete`, `altium365.testEvents.setDefault`. All registered once in `extension.ts` activation block; menu contributions reference them.
- **D-14:** **Post-UAT cleanup is a `package.json`-only edit.** Removing the losing surface = delete one menu group. No code refactor, no command-ID renames.

### Edit UI

- **D-15:** **JSON virtual document with JSONSchema.** `"Edit current…"` opens a virtual editor tab using a registered scheme (e.g., `altium365-event://<identity>/<eventName>.json`). On Cmd+S: parse, validate, commit to globalState. Reuses VS Code's built-in JSON editor (syntax highlighting, formatting, schema-driven autocomplete).
- **D-16:** **JSONSchema is bundled, not script-specific.** A single bundled schema describes the `project-related` shape (`projectId: string`) and allows additional properties. Script-specific schemas are deferred.
- **D-17:** **Save-bridge pattern mirrors Phase 6.** `onDidSaveTextDocument` listener for the virtual scheme dispatches to a commit handler. Same mental model as `registerLocalScriptSaveBridge` (`src/localScriptCache.ts:80-125`).
- **D-18:** **Built-in `project-related` preset.** When the user creates a new event, offer `project-related` as a starting template — `{projectId: ""}`. On first edit, optionally pre-fill `projectId` via `pickProjectId` (reuses Phase 6's shared picker at `src/projectPicker.ts:22`).

### Bloat / quotas

- **D-19:** **Soft warning only.** When an identity accumulates >25 events, show a warning toast on next create: "This script has N test events. Consider deleting unused ones." No hard cap. Defer quota enforcement to a future phase if it becomes a real problem.

### Resolver migration path

- **D-20:** **`resolveScriptParameters` is the unified entry point.** Replace today's two divergent code paths:
  - `prepareRun` in `extension.ts:790-870` — currently does sibling `.params.json` lookup + projectId prompt fallback inline. Replace with a single call to `resolveScriptParameters(identity)`.
  - `executeRemoteScript`'s Block B (`remoteExecution.ts:158-200`) — currently calls the local `resolveScriptParameters(ctx, scriptId)` at `:276` plus a projectId-prompt fallback at `:166-200`. Replace with the same unified call.
- **D-21:** **`resolveScriptParameters` returns `Array<{key, value}>` or `undefined`** — matches `GloScrScriptParameterInput[]`. All values stringified per the existing Pitfall 2 in `remoteExecution.ts:288`.
- **D-22:** **Projectid-prompt fallback from Phase 6 is removed once test-events ship.** The `altium365.promptForProjectId` setting becomes a no-op (kept for back-compat but documented as deprecated). The `project-related` preset replaces it functionally.

### the agent's Discretion

- Exact icon for the separate title-bar dropdown (Placement B) — pick a codicon that visually differentiates from the existing Altium 365 submenu icon. `$(zap)` or `$(symbol-event)` are reasonable candidates.
- Naming of the import marker key — `altium365.scriptParams.importedFrom.<identity>` is suggested but a different naming scheme is fine if it follows the existing prefix convention.
- Layout of the QuickPick when picker is invoked — single list with sections, or separator-grouped list. Use the most discoverable VS Code QuickPick pattern.
- Whether to show event JSON preview in the QuickPick `description`/`detail` slot when picking — yes if reasonable, no if it makes the picker noisy.

</decisions>

<specifics>
## Specific Ideas

- **AWS Toolkit Lambda test events** is the canonical UX reference. The picker is a flat QuickPick of named events with `Create new…` / `Edit current…` / `Delete…` actions at the bottom. The default event is invoked silently by the run button.
- **Both UI placements ship simultaneously** for A/B comparison. User explicitly stated: "I need to see them both to decide which one to keep. Design accordingly — assume that there will be only one place at the end." Implementation must make removal cheap.
- **fsPath fragility is accepted.** User: "if file is moved — the worst thing that happens, user will have to select the appropriate event from the global list again." Translated to the per-script model: user re-creates events on the new path. Documented in D-05.
- **Same UX regardless of local/remote distinction.** User: "Similar experience, regardless of local/remote distinction." Single picker, single editor, single resolver.

</specifics>

<deferred>
## Deferred Ideas

- **Cross-user test-event sharing** — round-trip events via a remote-stored blob (alongside the script in A365), so co-developers see the same events. Captured from roadmap open question. Belongs in a future phase after v1 ships and we have real usage data.
- **Hard storage caps / quota enforcement** — v1 ships a soft warning at 25 events per script (D-19). Real quota enforcement (delete-on-overflow LRU, per-user totals) belongs in a future phase if bloat becomes observed.
- **Structured form WebView editor** — JSON suffices for v1 (D-15). A form-based editor for non-technical users is a future polish phase.
- **Script-specific JSONSchemas** — v1 ships a single bundled schema for the `project-related` shape (D-16). Per-script schemas (e.g., declared in the script itself via a docstring annotation) are a future enhancement.
- **Migration tooling for flat `altium365-*.py` legacy tmp files** — out of scope here; Phase 6 D-11 already documented they purge naturally.
- **`altium365.promptForProjectId` setting removal** — kept as a deprecated no-op in v1 per D-22. Full removal is a future cleanup phase once telemetry confirms no one relies on it.

</deferred>
