## Summary

This phase replaces three divergent parameter sources (workspaceState blob, sibling `.params.json`, projectId-prompt fallback) with a single per-script test-events store, behind a single resolver. The technical risk is concentrated in **two surfaces only**:

1. **The writable virtual document** for editing event JSON.
2. **The dual editor/title placement** for A/B trial.

Both have well-trodden VS Code patterns; the existing codebase has already paid the integration cost for the first (the `altium365:` scheme is a `FileSystemProvider` — see `src/remoteScriptFs.ts:143`). The save-bridge pattern (`src/localScriptCache.ts:149`) is reused verbatim with a different scheme.

The rest is plain CRUD on `globalState`, a QuickPick picker, and `package.json` menu wiring. No GraphQL, no Python, no subprocess work.

**Primary recommendation:** Implement the virtual editor as a custom `FileSystemProvider` on scheme `altium365-event:` (NOT `registerTextDocumentContentProvider`, which is read-only). This matches the existing `altium365:` pattern, gives native Cmd+S handling, and avoids any "is the buffer dirty?" race conditions.

### Q1. VS Code virtual document scheme — writable editor tab

**Verdict: Use `FileSystemProvider` registered on a custom scheme (`altium365-event:`). Do NOT use `registerTextDocumentContentProvider`.** `[VERIFIED: codebase precedent + VS Code API docs]`

| Option | Writability | Cmd+S behavior | Verdict |
|---|---|---|---|
| `registerTextDocumentContentProvider` | **Read-only** by contract — the API returns `provideTextDocumentContent(uri): string`. Edits are buffer-local and cannot be saved. | Cmd+S triggers a Save-As dialog (wrong UX). | ❌ Reject |
| `FileSystemProvider` on custom scheme | Full read/write. `writeFile(uri, content, options)` is called on Cmd+S. | Native, transparent. | ✅ Use this |
| `untitled:` scheme + in-memory model | Writable, but every save prompts for file location (untitled = "user hasn't picked a path"). | Wrong UX. | ❌ Reject |
| `WorkspaceEdit.createFile` + in-memory tmp | Works but requires real on-disk file. | Polluting tmpdir for what is structured state. | ❌ Reject |

**Implementation sketch** (mirrors `AltiumRemoteScriptFs` at `src/remoteScriptFs.ts:143`):

```typescript
// src/testEvents/eventFs.ts
export class TestEventFs implements vscode.FileSystemProvider {
    private readonly _onDidChangeFile = new vscode.EventEmitter<vscode.FileChangeEvent[]>();
    readonly onDidChangeFile = this._onDidChangeFile.event;

    constructor(private readonly ctx: vscode.ExtensionContext) {}

    // URI shape: altium365-event://<identity>/<eventName>.json
    // identity may contain ':' (remote scriptId) — URL-encode in caller.

    stat(uri: vscode.Uri): vscode.FileStat {
        const { identity, eventName } = parseEventUri(uri);
        const store = readStore(this.ctx, identity);
        if (!store?.events[eventName]) {
            throw vscode.FileSystemError.FileNotFound(uri);
        }
        return { type: vscode.FileType.File, ctime: 0, mtime: Date.now(), size: 0 };
    }

    readFile(uri: vscode.Uri): Uint8Array {
        const { identity, eventName } = parseEventUri(uri);
        const store = readStore(this.ctx, identity);
        const payload = store?.events[eventName] ?? {};
        // Inject $schema for runtime JSONSchema fallback (see Q2)
        const withSchema = { $schema: BUNDLED_SCHEMA_URI, ...payload };
        return Buffer.from(JSON.stringify(withSchema, null, 2), 'utf-8');
    }

    async writeFile(uri: vscode.Uri, content: Uint8Array, _opts: { create: boolean; overwrite: boolean }): Promise<void> {
        const { identity, eventName } = parseEventUri(uri);
        let parsed: Record<string, unknown>;
        try {
            parsed = JSON.parse(Buffer.from(content).toString('utf-8'));
        } catch (e) {
            // Bubble — VS Code surfaces as save error toast
            throw vscode.FileSystemError.Unavailable(`Invalid JSON: ${(e as Error).message}`);
        }
        delete parsed.$schema; // strip transport-only field
        const store = readStore(this.ctx, identity) ?? { defaultEventName: '', events: {} };
        store.events[eventName] = parsed;
        if (!store.defaultEventName) store.defaultEventName = eventName;
        await writeStore(this.ctx, identity, store);
    }

    watch() { return new vscode.Disposable(() => {}); }
    readDirectory() { return []; }
    createDirectory() { /* no-op */ }
    delete(uri: vscode.Uri) { /* delegates to deleteEvent command */ }
    rename() { throw vscode.FileSystemError.NoPermissions(''); }
}
```

**Why this is better than the Phase 6 save-bridge pattern** for *this* phase: the FSP's own `writeFile` is the commit point, so there's no need for a separate `onDidSaveTextDocument` listener and no `doc.uri.scheme === 'file'` filter (the Phase 6 save-bridge tracks tmp `.py` files written by VS Code to disk; here the doc lives in the FSP itself). The save-bridge pattern in `localScriptCache.ts:149` is the **mental model reference**, not the literal copy target — D-17 should be interpreted as "save → commit, same idea," not "literal `onDidSaveTextDocument` listener required."

> **Note for planner:** D-17 in CONTEXT.md says "mirrors Phase 6." The intent is correct; the *mechanism* is cleaner via FSP `writeFile` than via a sibling listener. Recommend planner update D-17 wording during plan creation, or annotate the deviation. Either approach satisfies the user-visible contract (Cmd+S commits).

**Opening the editor:**

### Q2. JSONSchema attachment for virtual documents

**Verdict: Two-layer fallback — declarative `contributes.jsonValidation` with a `*.json` fileMatch + runtime `$schema` URL injection.** `[VERIFIED: VS Code docs; CITED: code.visualstudio.com/api/references/contribution-points#contributes.jsonValidation]`

`contributes.jsonValidation` works **by file glob applied to the URI's path component**. Globs like `**/*.json` will *usually* match virtual URIs whose path ends in `.json`, but support is inconsistent across schemes and not contractually guaranteed for non-`file:` URIs (the JSON language server's URI handling has been a moving target). Rather than relying on a single mechanism, ship both:

**Layer 1 — Declarative (`package.json`):**

```json
"contributes": {
  "jsonValidation": [
    {
      "fileMatch": ["altium365-event://**/*.json"],
      "url": "./schemas/test-event.schema.json"
    }
  ]
}
```

> Notes: `fileMatch` with a scheme prefix is supported as of VS Code 1.61+ (verify against project's `engines.vscode` `^1.85.0` — passes). If this doesn't bind in UAT, fall through to Layer 2 silently.

**Layer 2 — Runtime `$schema` injection (the always-works fallback):**

In `TestEventFs.readFile` (above), prepend a `$schema` URL pointing to the bundled schema served via the extension's own URI. Use the `vscode.Uri.file(context.asAbsolutePath('schemas/test-event.schema.json'))` and convert to a string. The JSON language server honours `$schema` regardless of scheme.

Strip `$schema` on write so it doesn't pollute the stored payload (sketch above does this).

**Bundled schema content** (per D-16 — single bundled schema, `additionalProperties: true`):

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "Altium 365 Test Event",
  "type": "object",
  "properties": {
    "projectId": { "type": "string", "description": "Altium 365 project GUID" }
  },
  "additionalProperties": true
}
```

**Confidence:** MEDIUM — Layer 1 has historical inconsistency for non-`file:` schemes; Layer 2 is bulletproof. Plan should call out the dual approach so planner doesn't drop one.

### Q5. Identity stability for standalone `.py` (D-05 trade-off survey)

**Verdict: No VS Code API survives external file renames. `vscode.workspace.onDidRenameFiles` only fires for renames performed through VS Code's own UI / refactor.** `[VERIFIED: VS Code API docs]`

|---|---|---|---|---|
| `fsPath` (D-04 locked) | ❌ | ❌ | ✅ | Simple, accepted per D-05 |

### Q6. Sibling `.params.json` import flow

**Verdict: `showInformationMessage` with action buttons; marker key stores absolute path of the imported file.** `[VERIFIED: VS Code API + existing codebase patterns]`

**Where to inject** — inside `resolveScriptParameters`, at the **start of the local-identity branch**, before the globalState read. NOT in `prepareRun` — keeping it inside the resolver means remote-script entry points never accidentally trigger the sibling-file lookup (remote scripts don't have a sibling file in the meaningful sense).

```typescript
async function maybePromptForSiblingImport(
    ctx: vscode.ExtensionContext,
    identity: string,            // = fsPath for local kind
): Promise<void> {
    const markerKey = `altium365.scriptParams.importedFrom.${identity}`;
    if (ctx.globalState.get<string>(markerKey)) return;             // already decided
    if (readStore(ctx, identity)) return;                            // events already exist
    const sibling = path.join(
        path.dirname(identity),
        `${path.basename(identity, path.extname(identity))}.params.json`
    );
    if (!fs.existsSync(sibling)) return;

    const choice = await vscode.window.showInformationMessage(
        `Found ${path.basename(sibling)} next to this script. Import as a test event?`,
        { modal: false },
        'Import', 'Not now', 'Never for this file'
    );
    if (choice === 'Never for this file') {
        await ctx.globalState.update(markerKey, '__declined__');
        return;
    }
    if (choice !== 'Import') return;  // 'Not now' or dismissed — re-prompt next run

    try {
        const raw = await fs.promises.readFile(sibling, 'utf-8');
        const parsed = JSON.parse(raw);
        const name = 'imported';
        await writeStore(ctx, identity, { defaultEventName: name, events: { [name]: parsed } });
        await ctx.globalState.update(markerKey, sibling);  // mark with the source path
        outputChannel.appendLine(`[Altium 365] Imported ${sibling} as test event '${name}'`);
    } catch (e) {
        vscode.window.showErrorMessage(
            `Altium 365: failed to import ${path.basename(sibling)}: ${(e as Error).message}`
        );
    }
}
```

**Why three buttons not two:** "Not now" (re-prompt next time) vs "Never for this file" (set marker, never re-prompt) is the AWS Toolkit / Git Lens convention and respects user agency. Two-button "Import / Cancel" would conflate "I'm busy" with "never ask again."

**Why `showInformationMessage` over QuickPick:** Modal QuickPick interrupts; toast is non-blocking and dismissable. The import is a one-time bootstrap, not a frequent flow.

**Confidence:** HIGH.

### Q8. `resolveScriptParameters` migration

**Verdict: Move to `src/testEvents/resolver.ts`. New signature returns a Promise.** `[VERIFIED: signature analysis against current call sites]`

**Current signature** (`remoteExecution.ts:276`):

```typescript
function resolveScriptParameters(
    ctx: vscode.ExtensionContext,
    scriptId: string
): Array<{ key: string; value: string }> | undefined
```

**New signature:**

```typescript
export type ScriptIdentity =
    | { kind: 'remote'; identity: string /* scriptId */ }
    | { kind: 'local'; identity: string /* fsPath */ };

export interface ResolveOptions {
    /**
     * When true (default), if no events exist for this identity, prompts the
     * user to create one (offering `project-related` preset). When false,
     * silently returns undefined — used by automated test paths or when the
     * caller wants to surface its own UI.
     */
    promptOnFirstRun?: boolean;
    /**
     * Workspace context needed by the `project-related` preset's pickProjectId
     * call. Pass undefined for standalone local scripts with no workspace context
     * — preset will fall back to the active workspace.
     */
    workspace?: WorkspaceContext;
}

export async function resolveScriptParameters(
    ctx: vscode.ExtensionContext,
    identity: ScriptIdentity,
    output: vscode.OutputChannel,
    options?: ResolveOptions
): Promise<Array<{ key: string; value: string }> | undefined>
```

**Why async:** the first-run prompt and the sibling-import flow are both async. Current sync signature precludes both.

**Why a discriminated union for identity:** The local branch needs the sibling-import lookup; the remote branch must not even check. Type-level discrimination > runtime sniffing.

**Implementation outline:**

```typescript
export async function resolveScriptParameters(ctx, identity, output, opts = {}) {
    // 1. Escape hatch: explicit setting wins (D-09).
    const explicit = vscode.workspace.getConfiguration('altium365').get<string>('inputParametersPath');
    if (explicit?.trim()) return readParamsFile(explicit);   // local-runner path needs file; for remote, parse + return

    // 2. Sibling-import bootstrap (local only).
    if (identity.kind === 'local' && opts.promptOnFirstRun !== false) {
        await maybePromptForSiblingImport(ctx, identity.identity);
    }

    // 3. Read store.
    const store = readStore(ctx, identity.identity);

    // 4. First-run prompt (D-11) — only if promptOnFirstRun and no events.
    if (!store || Object.keys(store.events).length === 0) {
        if (opts.promptOnFirstRun === false) return undefined;
        const created = await promptCreateFirstEvent(ctx, identity, opts.workspace, output);
        if (!created) return undefined;   // user cancelled
        return stringifyEvent(created);
    }

    // 5. No default → prompt to pick one (D-11).
    if (!store.defaultEventName || !store.events[store.defaultEventName]) {
        if (opts.promptOnFirstRun === false) return undefined;
        const picked = await promptPickDefault(ctx, identity, store);
        if (!picked) return undefined;
    }

    // 6. Silent default invocation (D-10).
    const event = store.events[store.defaultEventName];
    return stringifyEvent(event);
}

function stringifyEvent(obj: Record<string, unknown>): Array<{key: string; value: string}> {
    return Object.entries(obj)
        .filter(([_, v]) => v !== undefined && v !== null)
        .map(([k, v]) => ({ key: k, value: String(v) }));   // Pitfall 2 from remoteExecution.ts:288
}
```

**Subtlety for `prepareRun` (local runner) integration:** the runner takes a file path (`--params <file>`), not an in-memory object. After resolving the event, write to a tmpfile (same pattern as `extension.ts:839-848`):

```typescript
const params = await resolveScriptParameters(ctx, identity, output, {workspace, promptOnFirstRun: true});
if (params === undefined) return undefined;   // user cancelled
const tmpFile = path.join(os.tmpdir(), `altium365-params-${Date.now()}-${process.pid}.json`);
fs.writeFileSync(tmpFile, JSON.stringify(Object.fromEntries(params.map(p => [p.key, p.value])), null, 2), 'utf-8');
```

## Common Pitfalls

### Pitfall 1: URI encoding in `altium365-event://<identity>/<eventName>.json`

**What goes wrong:** `identity` for remote scripts is a UUID-shaped `scriptId` (safe). For local scripts it's an absolute `fsPath` containing `/`, `\\`, `:` (Windows drive), spaces, possibly Unicode. Naively concatenating into the URI breaks parsing.

**Fix:** `encodeURIComponent(identity)` on construction; `decodeURIComponent(uri.authority)` on parse. Use `uri.authority` not `uri.path[0]` because the slash-after-scheme delimiter is significant. Verify on Windows with `C:\\Users\\...\\script.py`.

**Warning sign:** `vscode.Uri.parse` returns a URI with the wrong `authority` / `path` split.

### Pitfall 2: `String(value)` stringification preserves `"null"` and `"undefined"`

Carry over the existing fix from `remoteExecution.ts:288-292`: filter `null`/`undefined` BEFORE `String()`. Already handled in the sketched `stringifyEvent` above; planner must not regress this.

### Pitfall 3: First-run prompt re-entrancy

If two run invocations race (user double-clicks the run button), both call `resolveScriptParameters`, both see no events, both open a create dialog. Use a per-identity in-memory `Map<string, Promise<...>>` lock (or `asyncMutex` — see `src/asyncMutex.ts`) to ensure only one create flow runs per identity at a time.

### Pitfall 4: `globalState` size limits

VS Code's `Memento` has no hard limit but is loaded synchronously at extension activation. Test-event objects are small (typical: <500 bytes); 25-event cap × N scripts × ~500B is sub-MB. Soft warning at 25 (D-19) is the right defense.

**Warning sign:** activation latency rising; check via `vscode.window.activeColorTheme` log timing. Not expected at v1 scale.

### Pitfall 5: JSON schema not binding to virtual URI

If the `jsonValidation` `fileMatch` doesn't catch the virtual URI (scheme-prefix glob support is inconsistent), the user sees no autocomplete. The `$schema` injection (Q2 Layer 2) is the bulletproof fallback. Plan should include a UAT check: "Open a test event in the editor → type a top-level `{` → autocomplete should suggest `projectId`."

### Pitfall 6: `onDidSaveTextDocument` fires for the FSP-backed doc

If implementing the save-bridge literally (per D-17 wording), be aware that the existing `registerLocalScriptSaveBridge` (`localScriptCache.ts:153`) filters `doc.uri.scheme !== 'file'` and exits — meaning it WILL NOT trigger on the `altium365-event:` scheme even with a literal copy of the pattern. **Good news:** the FSP's own `writeFile` is the commit point, no listener needed. **Bad news:** if a planner literally copies the save-bridge pattern, they'll wonder why the listener never fires. Document this explicitly in the plan.

### Pitfall 7: `editor/title` icon collision

If Placement B's icon is too similar to the existing `media/altium365.png` submenu icon, users won't visually distinguish them. UAT must include a screenshot comparison. `$(symbol-event)` is monochrome and clearly different from the colour brand mark.

### Pitfall 8: `promptForProjectId` deprecation timing

D-22 makes `promptForProjectId` a no-op. The existing `extension.ts:820-851` and `remoteExecution.ts:175-200` both read this setting. **Both must be removed in the same commit** as introducing the new resolver — otherwise the setting will be silently ignored by one call site and honoured by the other (worst-case state: inconsistent behaviour). The plan must sequence this as a single atomic change per call site.

### Pitfall 9: Sibling-import marker key for the same file across workspaces

The marker key `altium365.scriptParams.importedFrom.<fsPath>` is keyed on absolute path. If a user opens the same script in two different workspaces (e.g., as a symlink), the marker still applies — correct, because the events themselves are in `globalState` (cross-workspace). No fix needed; documenting for awareness.
