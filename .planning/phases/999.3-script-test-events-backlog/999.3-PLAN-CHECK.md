## FAIL — Blockers (must fix before execution)

### B-1. Data-shape contradiction: Plan 04 picker assumes fields that Plan 01 storage doesn't define

**Severity:** BLOCKER (will not compile)
**Dimension:** task_completeness / cross-plan data contract (Dim 9)
**Plans affected:** 999.3-04 vs 999.3-01

Plan 01 (foundation) defines:
```ts
interface TestEventStore { defaultEventName: string; events: Record<string, Record<string, unknown>>; }
```
— field is **`defaultEventName`**, events are plain JSON payloads with **no per-event metadata** (no `modifiedAt`, no timestamps).

Plan 04 Task 1 (picker.ts) specifies:
- Default-header row shown only if **`store.defaultName`** exists (wrong field — should be `defaultEventName`).
- Rows sorted by **`modifiedAt` desc** with detail `Last edited <relative-time>` (field doesn't exist; storage carries no timestamps).

Plan 04 Task 2 also writes:
- delete handler: "if deleted event was default, clear `defaultName`" (wrong field).
- setDefault handler: "Mutate store: `defaultName = name`" (wrong field).

Following Plan 04 literally produces a TS compile error AND a feature gap (timestamp-based sorting requires schema change).

**Remediation (small, atomic — do BEFORE executing Plan 04):**

1. In Plan 04 Task 1 action: replace all three occurrences of `store.defaultName` → `store.defaultEventName`. Drop the `sorted by modifiedAt desc` clause; instead sort by event name alphabetically (or insertion order via `Object.keys(events)`). Replace `detail: 'Last edited <relative-time>'` with a short single-line JSON preview (≤80 chars) per RESEARCH §Q3 recommendation.
2. In Plan 04 Task 2 action: replace both `defaultName` references with `defaultEventName` (delete handler + setDefault handler).
3. In Plan 04 Task 4 step 7: replace `defaultName` with `defaultEventName` in the UAT prose.
4. (Optional, defer) If timestamp sorting is genuinely wanted: add `modifiedAt: number` to each event payload via a `{ body, meta: { modifiedAt } }` envelope — but this is a scope expansion and should be deferred to a follow-up. RESEARCH §Q3 does not require timestamps.

This is a 6-line edit to `999.3-04-PLAN.md`. No re-planning needed.

### W-2. Plan 02 atomic commit relies on executor honoring "stage but don't commit" instructions
**Severity:** WARNING
Plan 02 Tasks 1 and 2 say "stage but don't commit; lands in Task 3's atomic commit." If `gsd-execute-phase` commits after each `<task type="auto">` by default (typical pattern), Pitfall 8 is silently violated — resolver.ts and importSibling.ts land in commit N, then prepareRun+Block B migration lands in commit N+1, leaving a window where the legacy resolver coexists with the new one.
**Fix options:** (a) Merge Tasks 1, 2, 3 into a single `<task>` with all four files in `<files>` so the executor commits once; (b) Add a "DO NOT COMMIT — STAGE ONLY" preamble in Task 1/2 `<action>` and a Task 3 verify gate `git log -1 --format=%s | grep -qE "^feat\\(999\\.3-02\\):.*Pitfall 8"` (Plan 02 has this gate, but it doesn't prevent earlier mid-stream commits). Recommended: option (a) collapses to one task.

### W-3. Plan 05 truth contradicts package.json reality on `when` clause
**Severity:** WARNING
Plan 05 `must_haves.truths` line 18 declares: `resourceScheme == 'file' && resourceExtname == '.py'`. The actual existing run-script `when` clause in package.json is `resourceLangId == python` (single condition). Plan 05 Task 1 action correctly instructs "COPY THE WHEN CLAUSE from the existing altium365.runScript" — so the implementer will likely produce the correct value. But the truth statement misleads anyone auditing the diff. Pitfall 7 (menu when clauses) is real and was raised in RESEARCH.
**Fix:** Replace the truth's hard-coded predicate with: "the same `when` clause as the existing `altium365.runScript` submenu row (currently `resourceLangId == python`)."

### W-4. Plan 03 jsonValidation glob may not match URI scheme paths
**Severity:** WARNING (hedged by Layer 2)
`contributes.jsonValidation.fileMatch: "altium365-event://**/*.json"` — VS Code's `jsonValidation.fileMatch` historically targets workspace-relative paths, not URI schemes. RESEARCH §Q2 explicitly hedges with the Layer 2 runtime `$schema` injection. If Layer 1 silently fails, autocomplete still works via Layer 2.
**Fix:** Plan 03 Task 3 UAT step 7 already detects total failure ("If no suggestions surface, the dual-fallback Layer-1 AND Layer-2 both failed → BLOCK, escalate"). No change needed; just be aware that Layer 1 may produce a benign console warning at extension load. Document in 03-SUMMARY.

### W-5. Plan 04 `must_haves.truths` mis-references D-22 for editor wiring
**Severity:** WARNING (cosmetic)
Plan 04 truth line 23 reads "[D-22] `edit` command opens `buildEventUri(identity, name)`..." — but D-22 is the `promptForProjectId` deprecation, not the editor scheme. Should be **D-15** (JSON virtual document scheme). Confusing for auditors.
