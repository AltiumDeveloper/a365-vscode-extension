## Decisions Made
- **"Run with empty params" removed** — the option was UX-broken: picking it returned `{}` to `doPickTestEvent` which only logs to outputChannel; the next script run still used the silent default. User correctly reported "default event is picked". Removed entirely; the `'empty'` member of the `PickerResult` union is retained as defensive dead-code in case a future feature wires a true force-empty run path.
- **"Edit current default…" detail line removed** — picker header already renders `Default: <name>` prominently; the redundant `detail` was visual noise.
- **Both A/B placements ship together** — D-12 specifies a dogfood-driven decision deferred to Plan 06+. Single command id (`altium365.testEvents.pick`) shared across both placements means observation is purely about which surface gets clicked, not about feature parity.
- **Placement B gating is `resourceLangId == python` only** — explicitly NOT `&& altium365.activeIsRemoteScript`. Local-only Python scripts also benefit from test events for local-run parameter management; restricting to remote scripts would have hidden the feature from half the use cases.
- **Submenu group `4_events@1`** — sorts last after existing `1_run / 2_remote / 3_publish` groups; chosen over interleaving to keep run-related actions grouped at the top.

## Deviations from Plan

## Issues Encountered

- **Picker UX bug surfaced during UAT** — "Run with empty params" was speccable from RESEARCH §Q3 but the actual pick command never executes anything, so the option was effectively a no-op. Fixed in `084c6ef` by removing the row. Lesson: speculative UX rows should be gated by "does the handler actually do something useful?" — if the answer is no, omit. Documented for Plan 06's polish pass to audit any other speculative affordances.
