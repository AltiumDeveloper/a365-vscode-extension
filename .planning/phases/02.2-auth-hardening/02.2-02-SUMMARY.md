# Phase 02.2 Plan 02: Refactor token-routing surface (D-01/D-02/D-03/D-04) Summary

Replaced the `SECRET_WORKSPACE_TOKENS` singleton with selection-routed token retrieval. `getActiveAccessToken` now reads the user's explicit workspace selection from `globalState` and delegates to `ensureWorkspaceToken` (workspace) or the new `getBaseAccessToken` (base). The singleton constant and its three secrets-store call sites are gone; `getStoredWorkspaceTokens` is removed from the export surface. CR-01 (cross-workspace token confusion) is closed at the API level — there is no longer any code path that could read or write the singleton. WR-05 carry-forward is unblocked: plan 02.2-06 can now wire `loadWorkspaces`/`pickAndExchangeWorkspace` to `getBaseAccessToken`.

## What Changed

- **Removed `SECRET_WORKSPACE_TOKENS`** constant and all three references:
    - `signIn` no longer calls `secrets.delete(SECRET_WORKSPACE_TOKENS)` (drain lands via plan 02.2-03 using `clearAllTokens`).
    - `exchangeWorkspaceToken` no longer calls `secrets.store(SECRET_WORKSPACE_TOKENS, …)` — it is now a pure HTTP wrapper that returns the exchanged token; `ensureWorkspaceToken` remains the sole cache writer using `SECRET_WS_TOKEN_PREFIX + workspaceId`.
    - `clearAllTokens` no longer calls `secrets.delete(SECRET_WORKSPACE_TOKENS)`; the per-workspace drain loop (via `GLOBAL_WS_TOKEN_INDEX_KEY`) already covers all per-workspace caches.
- **Removed `getStoredWorkspaceTokens`** (D-04) — exported function deleted entirely; no in-tree callers remain (grep verified across `src/`).
- **Added `getBaseAccessToken(context, cfg)`** (D-03) — extracted the refresh-on-expiry logic from the old `getActiveAccessToken`. Returns `Promise<string | undefined>`; on refresh failure, falls through with the stale token so the caller's 401-driven re-sign-in path can engage.
- **Rewrote `getActiveAccessToken(context, cfg)`** (D-02) — reads the selected workspace from `globalState`. When present, calls `ensureWorkspaceToken({ workspaceId, authId })` inside a `try/catch`; on exchange failure, falls back to `getBaseAccessToken` so the caller has SOMETHING to attempt. When no workspace is selected, delegates directly to `getBaseAccessToken`.
- **Added `GLOBAL_SELECTED_WORKSPACE_KEY`** constant (`'altium365.selectedWorkspace'`) co-located with other secret/globalState keys at the top of the file. This is the inline fallback documented in PLAN.md (`<interfaces>`) chosen over importing `getSelectedWorkspace` from `./workspace` — see Deviations.
- **Cleaned the misplaced `@deprecated` JSDoc** that was glued onto the `isExpired` declaration with no separating newline. The deprecation note referenced a function that no longer exists in this file, so deletion was the cleanest outcome (plan permitted either deletion or reformatting; executor's discretion).

## Deviations from Plan

### Documented Choices (per PLAN.md `<interfaces>` fallback)

**1. [PLAN.md-permitted] Used inline globalState read instead of importing `getSelectedWorkspace`.**

- **Reason:** `src/workspace.ts` already imports several symbols from `./auth` (line 11: `} from './auth';`). Importing `getSelectedWorkspace` back into `src/auth.ts` would introduce a circular import. The plan's `<interfaces>` block explicitly anticipated this and documented the inline `context.globalState.get<{ workspaceId; authId }>('altium365.selectedWorkspace')` fallback.
- **Implementation:** Added a private constant `GLOBAL_SELECTED_WORKSPACE_KEY = 'altium365.selectedWorkspace'` at the top of `src/auth.ts` (line 29) for symbol consistency with the other globalState/secrets keys, then used `context.globalState.get<{ workspaceId; authId }>(GLOBAL_SELECTED_WORKSPACE_KEY)` inside `getActiveAccessToken`.
- **Risk:** Magic-string drift — if `workspace.ts` ever renames its `globalState` key from `'altium365.selectedWorkspace'`, this constant must be updated in lock-step. Mitigation: a single grep gate in 02.2-06's plan can assert both files agree, and the constant name makes the contract obvious to future readers.
