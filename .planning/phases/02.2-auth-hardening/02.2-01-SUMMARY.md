# Phase 02.2 Plan 01: AsyncMutex Helper Summary

One-liner: Added a dependency-free, per-key `AsyncMutex` helper (`src/asyncMutex.ts`, 30 LOC) that serializes async work by string key with exception-safe lock release — the foundation for the D-07 race fix that plan 02.2-04 will wire into `ensureWorkspaceToken`.

## What Was Built

A single new file `src/asyncMutex.ts` exporting `class AsyncMutex` with one public method:

```ts
runExclusive<T>(key: string, fn: () => Promise<T>): Promise<T>
```

Semantics implemented:

- Same-key callers run strictly FIFO; the next `fn` starts only after the previous settles (resolve or reject).
- Different keys run in parallel — no global lock.
- A throwing/rejecting `fn` releases the key's lock before the rejection propagates (next waiter proceeds).
- The promise returned to the caller reflects `fn`'s outcome; the tail-chain promise is separately swallowed via `.catch(() => undefined)` so a failure cannot break the queue for the next caller.

No imports. No callers yet (wiring lands in plan 02.2-04). Zero behavioural change to the running extension.

## Decisions Made

- **API shape:** `runExclusive(key, fn)` over `acquire()/release()` — the closure-scoped form is exception-safe by construction (no path where a thrown error can skip the release). Matches CONTEXT's "simpler, exception-safe" guidance.
- **Tail-promise rejection handling:** Stored `run.catch(() => undefined)` rather than `run` directly. Without this, a rejected `fn` would propagate through the next `prev.then(...)` and either (a) skip the next `fn` entirely with the `.then(onFulfilled, onRejected)` form, or (b) leak the rejection to the next caller. Using `.then(() => fn(), () => fn())` for invocation + `.catch(() => undefined)` for the stored tail keeps the chain intact and isolates each caller's outcome.
- **No garbage collection:** Per D-07, the locks map may retain drained keys. Workspace count is bounded; cleanup is over-engineering.
