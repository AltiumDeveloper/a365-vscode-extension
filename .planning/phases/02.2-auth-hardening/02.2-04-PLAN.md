    Modify `src/auth.ts`:

    1. At the top of the file (after the existing `import { URL, URLSearchParams } from 'url';` line), add: `import { AsyncMutex } from './asyncMutex';`.

    2. Above `ensureWorkspaceToken` (or near the other module-local constants like SECRET_TOKENS), add a module-level mutex instance: `const workspaceTokenMutex = new AsyncMutex();`. This is a single-purpose helper analogous to `outputChannel` and the `authStateEmitter` (already documented CONVENTIONS exception); add a short JSDoc line explaining its role.

    3. Refactor `ensureWorkspaceToken` body to the following shape (directive prose — executor writes the code):

       a. **Fast path (outside mutex):** Read `SECRET_WS_TOKEN_PREFIX + workspace.workspaceId`. If the raw value parses to a TokenSet with `access_token` set and `!isExpired(parsed)`, return `parsed.access_token` immediately. This keeps uncontended cache hits lock-free.

       b. **Slow path (inside mutex):** Call `return await workspaceTokenMutex.runExclusive(workspace.workspaceId, async () => { ... })`. Inside the callback:

          - **Re-check the cache first** (double-checked locking): re-read the same secret key. If a concurrent caller populated it while this one was queued, parse and return `parsed.access_token` (still validate `!isExpired`). This is the dedup mechanism — the second of two concurrent callers must see the first caller's freshly-stored token.

          - If the cache is still empty/expired, call `await exchangeWorkspaceToken(context, cfg, workspace.authId)` to fetch a fresh token, then `await context.secrets.store(key, JSON.stringify(fresh))`.

          - Read `context.globalState.get<string[]>(GLOBAL_WS_TOKEN_INDEX_KEY, [])`. If `!index.includes(workspace.workspaceId)`, write back `[...index, workspace.workspaceId]` via `await context.globalState.update(GLOBAL_WS_TOKEN_INDEX_KEY, next)`. Because the entire callback runs under the per-workspaceId lock, two concurrent callers for the same workspace cannot both read a stale index and both append (which would still be safe because of the includes-check, but would still represent the race condition WR-05 flagged — closing it conceptually is the point).

          - Return `fresh.access_token`.

       Note on the index-update race specifically: WR-05's strict reading is about the read-modify-write of the index. The per-workspaceId mutex serializes index updates for the SAME workspaceId, but concurrent updates for DIFFERENT workspaceIds still interleave. This is safe because `context.globalState.update` is sequenced internally by VS Code (it returns a Thenable that completes after persistence), AND each entry's `includes` check is idempotent — two different workspaces both appending different ids cannot collide on the SAME slot. If a stricter single-writer guarantee is desired later, the planner notes this can be tightened to a global key like `'__index__'` for the index-update sub-step only, but D-07's "keyed by workspaceId" rule takes precedence and this looser model is acceptable per the existing globalState concurrency semantics. Do NOT introduce a global lock — that was explicitly called out as an anti-pattern in CONTEXT.md.

    4. Behaviour on exchange failure: if `exchangeWorkspaceToken` throws inside the callback, the AsyncMutex from plan 02.2-01 releases the lock on rejection (verified by the asyncMutex acceptance criteria). The error propagates to the caller unchanged — extension.ts command handlers already surface auth errors via `vscode.window.showErrorMessage`.
