# Phase 02.2 — Auth Hardening: Manual UAT

This script verifies the six in-scope findings (CR-01, CR-02, WR-01, WR-02, WR-04, WR-05) for phase
`02.2-auth-hardening` before the phase is marked complete. Per D-13, no automated logging or telemetry
was added — verification is by manual inspection of the UI, the VS Code Developer Tools network log,
and the extension's OutputChannel ("Altium 365").

Run all five scenarios in order. For each, tick **PASS** or **FAIL**. If any fails, capture details in
the "Overall result" notes section at the bottom.

Setup once before starting:

1. Launch the Extension Development Host (F5) against a fresh build (`npm run compile`).
2. Open the OutputChannel: View → Output → select **Altium 365** from the dropdown.
3. Open the Developer Tools: Help → Toggle Developer Tools → switch to the **Network** tab and filter
   for the GraphQL endpoint and the token endpoint of the active environment.

---

## Scenario 1: Account switch without explicit sign-out (CR-02 / D-05)

**Preconditions**

- Extension is signed out (run `Altium 365: Sign Out` first if needed).
- Two valid Altium 365 identities **A** and **B** are available for the same environment.

**Steps**

1. Run `Altium 365: Sign In` from the command palette and authenticate as identity **A**.
2. In the A365 side panel, expand any workspace. Confirm the per-workspace token cache is populated —
   either by inspecting `altium365.workspaceTokens.<workspaceId>` in SecretStorage via Developer
   Tools → Application, **or** by collapsing and re-expanding immediately and observing no second
   token-endpoint exchange in the network log.
3. **Without** running `Altium 365: Sign Out`, run `Altium 365: Sign In` again and authenticate as
   identity **B**.
4. After sign-in completes, run `Altium 365: Refresh Tree` and expand the same workspace as in step 2.

**Expected**

- A fresh token-endpoint exchange happens for that workspace under identity **B** (visible in the
  OutputChannel and/or network log).
- Identity **A**'s per-workspace token cache is gone — there is no path by which A's token can be
  returned to B's session (verify by inspecting SecretStorage: the old `altium365.workspaceTokens.*`
  entries are absent).
- No UI flicker to a signed-out state during the B sign-in (the tree does not collapse to an
  unauthenticated placeholder mid-flow).

- [ ] PASS
- [ ] FAIL

## Scenario 2: Parallel workspace expansion (WR-05 race / D-07 dedup)

**Preconditions**

- Signed in with an account that has at least **3 workspaces** visible in the A365 tree.
- OutputChannel and network-log filters as in Setup are visible.

**Steps**

1. Collapse all top-level tree nodes.
2. Run `Altium 365: Refresh Tree`.
3. Immediately expand 3 or more workspaces in rapid succession (within roughly 1 second of each
   other — fast clicks down the tree).

**Expected**

- Exactly **N** token-endpoint exchanges occur, one per distinct workspace expanded (visible in the
  network log / OutputChannel).
- **No duplicate** token exchanges for the same workspace, even though the expansions overlapped.
- The `altium365.workspaceTokens.__index` entry in SecretStorage ends up containing exactly **N**
  workspace IDs (no lost writes from the prior read-modify-write race on the index).

- [ ] PASS
- [ ] FAIL

## Scenario 3: Expired base token triggers refresh (WR-02 / D-09)

**Preconditions**

- Signed in.
- The stored base token has a valid `refresh_token` (true for any normal sign-in via this extension).

**Steps**

1. Manually expire the base token. Either:
   - **(a)** Open Developer Tools → Application → SecretStorage, locate the value at key
     `altium365.tokens`, and edit `expires_at` to a past Unix timestamp (e.g. `1`); **or**
   - **(b)** Wait for natural expiry of the base token.
2. Run `Altium 365: Refresh Tree` (which calls `loadWorkspaces`).

**Expected**

- The `refresh_token` grant is sent transparently to the token endpoint (visible in the network log).
- A fresh base token is written back to `altium365.tokens` in SecretStorage with a future
  `expires_at`.
- The tree loads successfully with the user's workspaces.
- **No** 401 error surfaces to the user, and **no** re-sign-in prompt appears.

- [ ] PASS
- [ ] FAIL

## Scenario 4: listWorkspaces always uses the base token (WR-05 carry-forward / D-03, D-09, D-10)

**Preconditions**

- Signed in.
- A workspace is currently selected — either via `Altium 365: Select Workspace`, or by having
  expanded a workspace previously in this session (so a workspace-scoped token exists at
  `altium365.workspaceTokens.<workspaceId>`).

**Steps**

1. Open Developer Tools → Network and filter for the GraphQL endpoint of the active environment.
2. Run `Altium 365: Refresh Tree`.
3. Locate the `desWorkspaceInfos` (listWorkspaces) request in the network log and inspect its
   `Authorization` header.

**Expected**

- The `Authorization: Bearer …` value is the **base token** — the one stored under
  `altium365.tokens` — **not** the workspace-scoped token stored under
  `altium365.workspaceTokens.<workspaceId>` for the currently-selected workspace.
- To distinguish the two, copy the JWT payload (the middle base64url segment) into any JWT decoder:
  - The **base token** payload **lacks** any `a365:workspace:<authId>` scope claim.
  - The **workspace-scoped token** payload **includes** an `a365:workspace:<authId>` scope claim
    matching the selected workspace.

- [ ] PASS
- [ ] FAIL

## Scenario 5: OAuth error XSS hardening (WR-01 / D-11)

**Preconditions**

- Extension is running.
- A sign-in flow is active (so the loopback OAuth callback server is listening on the configured
  redirect port and path).

**Steps**

1. Run `Altium 365: Sign In` to open the loopback listener. Note the configured redirect port and
   path (see the extension settings or the OutputChannel log line emitted when the listener starts).
2. Instead of completing the real OAuth flow in the browser that opened, manually navigate any
   browser to a crafted error callback URL of the form:

   ```
   http://localhost:<redirectPort><redirectPath>?error=<img src=x onerror=alert(1)>
   ```

   Substitute `<redirectPort>` and `<redirectPath>` with the actual configured values (e.g.
   `http://localhost:53682/callback?error=<img src=x onerror=alert(1)>`). URL-encoding the payload
   is fine — the loopback server should still produce the escaped output.
3. Observe the response page rendered by the loopback server in the browser.

**Expected**

- The page renders the **literal escaped text** `<img src=x onerror=alert(1)>` as visible
  characters on the page. Viewing page source shows it as HTML-escaped (e.g.
  `&lt;img src=x onerror=alert(1)&gt;`).
- **No** browser `alert(1)` dialog appears.
- **No** script executes (Developer Tools console shows no execution from the injected payload; no
  network request is fired by the payload).

- [ ] PASS
- [ ] FAIL
