    Write exactly the five scenarios from D-14 (the planner does not invent new ones):

    **Scenario 1 — Account switch without explicit sign-out (validates CR-02 / D-05):**
      - Preconditions: extension is signed out; two valid Altium 365 identities A and B are available.
      - Steps: (1) Sign in as A via command palette. (2) In the side panel, expand any workspace and confirm the per-workspace token cache is populated (via Developer Tools → Application → check secret storage, OR confirm by re-expanding immediately and seeing no second network exchange). (3) WITHOUT signing out, run "Altium 365: Sign In" again and authenticate as B. (4) After sign-in completes, trigger a tree refresh and expand the same workspace.
      - Expected: A new token exchange happens for that workspace under identity B (visible in the OutputChannel or network log). A's per-workspace cache is gone — there is no possibility of A's token being returned to B's session. No UI flicker to a signed-out state during the B sign-in.

    **Scenario 2 — Parallel workspace expansion (validates WR-05 race + D-07 dedup):**
      - Preconditions: signed in with an account that has at least 3 workspaces visible in the tree.
      - Steps: (1) Collapse all tree nodes. (2) Run "Altium 365: Refresh Tree" (or the equivalent command). (3) Immediately expand 3 or more workspaces in rapid succession (within ~1 second).
      - Expected: Exactly N token exchanges occur (one per workspace), visible in the network log / OutputChannel. NO duplicate exchanges for the same workspace. The globalState index ends up containing exactly N entries (no lost writes from the index read-modify-write race).

    **Scenario 3 — Expired base token triggers refresh (validates WR-02 / D-09):**
      - Preconditions: signed in; the base token has a valid refresh_token.
      - Steps: (1) Manually expire the base token. Either (a) open Developer Tools → Application → SecretStorage, edit the value at key `altium365.tokens` to set `expires_at` to a past timestamp, OR (b) wait for natural expiry. (2) Trigger a tree refresh (which calls loadWorkspaces).
      - Expected: The refresh_token grant runs transparently against the token endpoint, a fresh base token is stored, and the tree loads successfully. NO 401 surfaces to the user; NO re-sign-in prompt appears.

    **Scenario 4 — listWorkspaces always uses the base token (validates WR-05 carry-forward / D-03, D-09, D-10):**
      - Preconditions: signed in; a workspace is currently selected (via "Altium 365: Select Workspace" or by having expanded one previously).
      - Steps: (1) Open the VS Code Developer Tools network log and filter for the GraphQL endpoint. (2) Trigger a tree refresh. (3) Inspect the Authorization header of the listWorkspaces request.
      - Expected: The Authorization bearer token for the `desWorkspaceInfos` query is the BASE token (the one stored under `altium365.tokens`), NOT the workspace-scoped token for the selected workspace (stored under `altium365.workspaceTokens.<workspaceId>`). Distinguishing the two: decode the JWT payload — the base token will lack the `a365:workspace:<authId>` scope claim; the workspace-scoped token will include it.

    **Scenario 5 — OAuth error XSS hardening (validates WR-01 / D-11):**
      - Preconditions: extension is running and the loopback OAuth callback server can be reached (sign-in flow active OR the callback port is open during a sign-in attempt).
      - Steps: (1) Start a sign-in to open the loopback listener. (2) Instead of completing the real OAuth flow, manually visit a crafted callback URL in any browser: `http://localhost:<redirectPort><redirectPath>?error=<img src=x onerror=alert(1)>` (substitute the configured port and path). (3) Observe the response page rendered by the loopback server.
      - Expected: The page renders the literal escaped text "`<img src=x onerror=alert(1)>`" (or the HTML-escaped equivalent visible in page source as `&lt;img src=x onerror=alert(1)&gt;`). NO browser alert dialog appears. NO script executes.

    After the five scenarios, add a short "Overall result" section with checkboxes for "All scenarios passed" and "One or more scenarios failed (see notes below)" plus a free-form notes area for the tester.

The token-endpoint error-body truncation (D-12) does NOT have a manual scenario by design — it is a defensive code change verified by reading the diff; if the developer wants to test it, they can point the tokenEndpoint setting at a deliberately-broken URL, but this is not required.
