# Phase 02.2 Plan 04: Mutex-Guarded ensureWorkspaceToken Summary

Wired `AsyncMutex` from plan 02.2-01 into `ensureWorkspaceToken` to serialize the cache-miss path per workspaceId — closes 02-REVIEW WR-05 (index RMW race) and dedupes concurrent token exchanges for the same workspace on cold-start tree expansion.

## What Changed

`src/auth.ts`:
1. Added `import { AsyncMutex } from './asyncMutex';`.
2. Added module-level `const workspaceTokenMutex = new AsyncMutex();` with JSDoc citing the same CONVENTIONS exception as `authStateEmitter`.
3. Refactored `ensureWorkspaceToken`:
   - **Fast path (unchanged, outside mutex):** read secret, return on fresh cache hit.
   - **Slow path:** wrapped in `workspaceTokenMutex.runExclusive(workspace.workspaceId, async () => { ... })`.
     - Inside the callback: re-read the secret (double-checked locking) and return the cached token if a concurrent caller populated it.
     - Otherwise: call `exchangeWorkspaceToken`, store the result, then perform the index read-append-write under the same lock.

## Behavioural Properties

| Property | Mechanism |
| --- | --- |
| Concurrent calls, same workspaceId → 1 exchange | FIFO queue on the workspaceId key; double-checked re-read returns cached token to subsequent waiters |
| Concurrent calls, different workspaceIds → parallel | `AsyncMutex.runExclusive` only serializes per-key; different keys are independent |
| Fast-path cache hits → lock-free | Initial read happens BEFORE `runExclusive` |
| Failed exchange → lock released | `AsyncMutex` stores `run.catch(() => undefined)` as the tail (verified in plan 02.2-01); the next waiter proceeds |
| Index RMW race (WR-05) → closed | Read/append/write of `GLOBAL_WS_TOKEN_INDEX_KEY` now executes inside the per-workspaceId lock |
